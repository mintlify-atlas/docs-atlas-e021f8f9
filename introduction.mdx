SQLite is a relational database management system unlike any other: instead of running as a separate server process that clients connect to over a network, SQLite is a C library that you link directly into your application. The entire database — tables, indexes, triggers, views, and all stored data — lives in a single ordinary file on disk. There is no installation step, no daemon to start, no configuration file to edit, and no administrator to consult. Your application opens a file, runs SQL, and closes it. That's all there is to it.

## How SQLite Differs from Client-Server Databases

Traditional database systems such as PostgreSQL and MySQL follow a **client-server model**: the database engine runs as a long-lived background process (the server), and applications communicate with it by sending messages over a network socket — even when the application and the database reside on the same machine. This model adds operational overhead (process management, authentication, connection pooling, network configuration) but is well-suited for environments where many independent clients need concurrent access to shared, centrally-managed data.

SQLite takes the opposite approach. The library is **in-process**: it runs inside the application's own address space, reading and writing files directly using normal OS calls. There is no inter-process communication, no serialization protocol, no server to crash, and no port to open. The tradeoff is that simultaneous write access from multiple processes is limited to what the operating system's file-locking primitives can provide — excellent for most embedded and single-user scenarios, but different in character from a dedicated server.

| Property | SQLite | PostgreSQL / MySQL |
|---|---|---|
| Architecture | In-process library | Client-server daemon |
| Configuration | Zero-config | Server setup required |
| Network access | None (local files) | TCP/IP socket |
| Multi-writer concurrency | Serialised via file locks | Fine-grained row-level locks |
| Database format | Single file | Data directory |
| Deployment | Copy a file | Install + configure server |

## Current Version

SQLite **3.54.0** is the current release. The version is exposed at compile time via the `SQLITE_VERSION` preprocessor macro defined in `sqlite3.h`, and at runtime via `sqlite3_libversion()`:

```c
#include "sqlite3.h"
#include <stdio.h>

int main(void) {
    printf("SQLite version: %s\n", sqlite3_libversion());
    /* Prints: SQLite version: 3.54.0 */
    return 0;
}
```

## The Amalgamation

The standard way to embed SQLite into an application is through the **amalgamation**: a pair of files generated by concatenating all of SQLite's individual C source modules into one translation unit.

| File | Purpose |
|---|---|
| `sqlite3.c` | The complete SQLite implementation (~250 000 lines of C) |
| `sqlite3.h` | The public C API header — include this in your application |

The amalgamation is distributed as part of the official release packages. Building it from the canonical source tree requires running:

```bash
./configure
make sqlite3.c
```

Compiling the amalgamation as a single translation unit lets the C compiler see all of SQLite simultaneously, enabling aggressive inlining and optimization across module boundaries. The resulting binary is faster than a separately-compiled multi-file build.

<Note>
  The amalgamation (`sqlite3.c` + `sqlite3.h`) is the **recommended integration path** for embedding SQLite in applications. You do not need to build a shared library or install anything system-wide — simply add these two files to your project.
</Note>

## Source Tree Overview

The canonical SQLite source repository is organized as follows:

<Accordion title="src/ — Core database engine">
  Contains the C source files for the complete SQLite implementation, including the SQL parser (`parse.y`, processed by Lemon), the byte-code virtual machine (`vdbe.c`), the B-tree storage engine (`btree.c`), the query planner (`where.c`, `select.c`), the pager and WAL (`pager.c`, `wal.c`), memory management, and the main public API entry points (`main.c`). The public API is specified in the template header `sqlite.h.in`, from which `sqlite3.h` is generated.
</Accordion>

<Accordion title="ext/ — Optional extensions">
  Houses loadable and built-in extensions that are not part of the SQLite core but ship with the source tree. Notable subdirectories include `fts5/` (full-text search), `rtree/` (R-tree spatial index), `session/` (change-set and patch-set generation), `rbu/` (resumable bulk update), `jni/` (Java Native Interface bindings), and `wasm/` (WebAssembly build support).
</Accordion>

<Accordion title="tool/ — Build and maintenance utilities">
  Contains scripts and programs used to build, test, and maintain SQLite. This includes `mkkeywordhash.c` (generates the SQL keyword hash table), `lemon.c` (the LALR parser generator used to compile `parse.y`), and various Tcl scripts used by the test suite and the amalgamation build process.
</Accordion>

<Accordion title="test/ — Test suite">
  SQLite ships with an extensive test suite comprising thousands of Tcl scripts and C programs. The full test suite exercises virtually every code path, including error injection, fuzzing, and crash recovery scenarios.
</Accordion>

## Core Use Cases

SQLite is the most widely deployed database engine in the world, appearing in every smartphone, most web browsers, many desktop applications, and countless embedded systems. Common applications include:

- **Mobile applications** — Android and iOS both use SQLite as their native local storage engine.
- **Desktop applications** — Media players, email clients, and productivity tools use SQLite for local data persistence.
- **Embedded systems** — IoT devices, automotive infotainment systems, and industrial controllers use SQLite because it requires no operating-system services beyond basic file I/O.
- **Application file format** — SQLite databases serve as structured, self-describing file formats — a better alternative to CSV, XML, or JSON for complex structured data.
- **Testing** — Application test suites swap out client-server databases for SQLite to eliminate infrastructure dependencies and speed up test runs.
- **Data analysis and ETL** — The `sqlite3` CLI and language bindings make SQLite an effective tool for exploring and transforming datasets on a local machine.
